0What we built

A school administrator can open Permishly, log in with an email and password, and see their school board and the schools they run. The boards and schools are demo data that the seeds load. There is no screen to create them yet.

Most of the code is not the login form. Permishly is multi-tenant: one installation serves many school boards, and data from one board must never reach another. architecture.md says this must be in place before the first table that holds board data. The users table is such a table, so login had to be built on top of that foundation.

The walkthrough follows the layers in the order a request passes through them, from the database up to React. Each part says what the code does and why it is there.

1The tables

Two kinds of table exist. A global table has no board column and is shared by the whole installation. A tenant table has an organization_id column, and each row belongs to one board.

TableKindHolds
organizationsGlobalA school board (or an independent school). This is the tenant.
identitiesGlobalEmail and password digest. One per person.
sessionsGlobalA login. The identity, and the board picked (null until picked).
schoolsTenantName and IANA time zone.
usersTenantThe person inside one board: name, and the identity they log in with.
school_administratorsTenantWhich user runs which school.

Why split identities from users? A person can work in two boards. They should have one password, but two separate sets of data and roles. So the password lives once, globally, and each board has its own user row that points to the identity.

The unique index on (organization_id, identity_id) means a person has at most one user in each board. The index on identity_id alone serves the login lookup in part 5.

Every table uses a UUIDv7 primary key from Postgres's uuidv7(). Nobody can guess the next ID, and the IDs still sort by creation time.

2Row-level security

Postgres row-level security (RLS) lets a table carry a filter that the database applies to every query. We use it so that a query that forgets WHERE organization_id = … still cannot see another board's rows.

Every tenant table is created with one helper, so no table can be made without the policy:

What each part is for:

  • ENABLE and FORCE ROW LEVEL SECURITY. Enable turns the policy on. Force applies it to the table owner too. Without force, the owner sees all rows.
  • The policy. A row is visible, and writable, only when its organization_id equals the session setting app.organization_id. The policy has no separate WITH CHECK, so Postgres uses the same rule for inserts and updates. You cannot write a row for another board.
  • NULLIF(…, ''). After a transaction that set the value ends, Postgres returns an empty string for it, not null. ''::uuid raises an error. With NULLIF the comparison is against null, so no rows match. The rule is: no board set means no rows.
  • The (organization_id, id) unique index lets other tenant tables point at a row by board and ID together.
  • add_tenant_reference makes a composite foreign key on (organization_id, school_id). A school administrator row in board A cannot point to a school in board B, because the pair (A, school-in-B) does not exist.

The schema file is db/structure.sql, not schema.rb, because schema.rb cannot store policies. config/application.rb sets this, and also turns on strict_loading_by_default, so associations must be loaded explicitly and N+1 queries raise errors:

3Database roles

RLS has one large hole: a superuser, or any role with BYPASSRLS, ignores every policy. The Docker Postgres user permishly is a superuser. If the app connected as that user, all the policies above would do nothing.

So there are three roles:

RoleUsed byRLS
permishly (owner)Migrations, schema loads, seedsBypasses
permishly_appThe running app, job workers, and the specsApplies
permishly_cross_tenant_readerOwns the one function that reads across boards (part 5). Cannot log in.Bypasses

config/database.yml has two configs for each database. Rails connects the app to primary, the app role. database_tasks: false tells Rails not to run migrations through it. The owner config is the one migrations use.

The app role needs GRANTs on every table. Rails writes structure.sql with pg_dump --no-privileges --no-owner, and those flags are hard-coded. Grants put in a migration would be lost the next time someone loads the schema. So the grants live in their own file, written so that it is safe to run again and again:

A rake file applies it after every task that changes the schema. It also fixes a trap: some Rails tasks, for example db:migrate:redo, use the default ActiveRecord::Base connection, which is now the app role. The app role cannot change the schema, so the first block below points all db: tasks at the owner.

4Setting the current board

The policy reads app.organization_id. Something has to set it. Tenancy.with_organization sets it for one block of code:

  • set_config(…, true) is the function form of SET LOCAL. The value lasts only until the transaction ends. That is why the block runs inside a transaction.
  • Restore on exit. Rails joins nested transactions into one. If a block for board A ran inside a longer transaction, the setting would stay after the block ended. The ensure puts the previous value back. Specs depend on this: the whole spec runs in one transaction, so without the restore, a board set in a spec's setup would still be set during the request under test.
  • The rescue in restore. After a database error, Postgres rejects every statement until rollback. Restoring would raise a second error and hide the first. The rollback drops the setting anyway, so we skip it in that one case.

The spec that proves all this runs as the app role. Its first example checks that, because a spec that ran as a superuser would pass whatever the policy said:

5The one read across boards

Login has a problem. Before the person is logged in, no board is set, so RLS hides every user row. But to log in we must find which boards this identity has users in.

architecture.md says to solve this with a narrow database function, not by giving the app a role that bypasses RLS:

  • SECURITY DEFINER runs the function with its owner's rights. db/privileges.sql makes permishly_cross_tenant_reader the owner. That role has BYPASSRLS, but it can read only two columns of users, and nobody can log in as it.
  • It returns board IDs only, not names or user data. The caller reads names from organizations, which is global anyway.
  • SET search_path stops a caller from creating a look-alike users table in another schema to trick the function.
  • Only permishly_app can run it. PUBLIC loses EXECUTE.

6Commands, queries and results

The architecture uses commands for writes and queries for reads. A controller never touches models directly. It calls a command or query and gets back a UseCaseResult: a success with a value, or a failure with a category and a list of errors.

The category decides the HTTP status (part 8). unauthenticated was added for this feature: 401, for "not logged in" and "login failed".

Commands and queries share one shape, held in a concern:

  • Inputs are ActiveModel attributes. They are typed, and validates works on them.
  • Every use case has an organization_id input, required by default. A class that does global work, such as login, opts out with runs_without_organization. The default is the safe one: forgetting the declaration gives a validation failure, not unscoped access.
  • call splits its keywords. The architecture shows both call(inputs, fake: x) and RosterQuery.call(school_id:, page:). Keywords that name a declared dependency are dependencies, and the rest are inputs.
  • The ActiveModel modules are included at module level, not inside included do. If they were in that block, their initialize would come first in Ruby's lookup order and hide ours. That was the first bug the specs found.

A command validates, opens a transaction, sets the board, runs perform, and rolls back if perform returns a failure:

A query runs in a read-only transaction and blocks writes in Active Record too:

Two details here came from bugs:

  • read_only is computed before transaction opens. The first version checked it inside the block, where a transaction is always open, so no query was ever read-only. The specs could not see this, because every spec runs inside a transaction. A spec with use_transactional_tests = false now checks SHOW transaction_read_only returns on.
  • ActiveRecord::Base.while_preventing_writes, not ApplicationRecord. The connection pool belongs to ActiveRecord::Base. Called on ApplicationRecord, the guard did nothing.

7The login logic

The Authentication capability owns identities and sessions. Its code is in app/capabilities/authentication/.

Log in

  • authenticate_by (Rails 7.1+) takes the same time when the email is unknown as when the password is wrong. Otherwise an attacker could time the response to learn which emails have accounts.
  • One message for both cases, for the same reason.
  • One board: the session is in it at once. More than one: organization_id stays null and the person picks. Login never lists boards before the password is correct, because that would tell anyone which boards an email belongs to.
  • It returns only the session ID. The controller puts that in the cookie.

The base controller turns a result into a response, using the table from architecture.md:

The cookie. The app is API-only, so config/application.rb adds the cookie middleware back, and the base controller includes ActionController::Cookies.

  • Signed: the browser cannot change the session ID. A spec sends a real session ID in an unsigned cookie and gets 401.
  • httponly: JavaScript on the page cannot read it, so a script injected into the page cannot steal it.
  • same_site: :lax: browsers do not send it with a POST from another site. This is the only CSRF protection for now, and todo.md asks whether we need more.

The controller is thin. Logging in is rate limited with Rails 8's rate_limit: ten tries in three minutes for each IP address.

12Traps worth knowing

These cost time while building the feature. They are easy to hit again.

A superuser ignores RLS
Even with FORCE. Check the connection role before you trust a passing isolation test.
A reset setting is an empty string
current_setting returns '', not null, after a transaction that set it ends. Cast it with NULLIF.
db:migrate on an empty database loads structure.sql
It does not run the migrations. A stale structure.sql gives you a stale database. Delete it and migrate when you change a migration that already ran.
pg_dump must be the server's version or newer
Rails runs your local pg_dump. The server is Postgres 18. Homebrew libpq had to go from 17 to 18.
Grants do not survive a schema load
Rails dumps with --no-privileges --no-owner. Put grants and function owners in db/privileges.sql.
A test transaction hides transaction bugs
Anything about "the first statement in a transaction" needs a spec with use_transactional_tests = false.
A method name can hide a class attribute
A private method called organization_required silently replaced the attribute reader of the same name. The attribute is now requires_organization, readable only on the class.

13Not done yet

  • Sessions never expire. The cookie is permanent and the server keeps old sessions.
  • CSRF protection is SameSite=Lax only.
  • No Google login.
  • No screens or commands to create boards, schools or users. The seeds write directly.
  • No authorization model yet. "School administrator" is a table, not a role with permissions.
  • Production needs PRIMARY_DATABASE_URL and OWNER_DATABASE_URL, and a password for permishly_app.

These are listed in todo.md.
